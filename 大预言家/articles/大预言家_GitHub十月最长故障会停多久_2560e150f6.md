# GitHub十月最长故障会停多久

GitHub十月最长一次关键故障会停多久，Polymarket最靠前的答案是3至6小时，约84%。6至12小时约9%，12小时以上约4%。成交量只有2.2万美元，但它对应的是开发者每天都会抱怨、也每天离不开的那种基础设施：代码还在，项目也在，按钮却不一定会动。

10月12日的GitHub事件已经持续了大约八个半小时，Actions、Pull Requests和Issues等服务都受到影响。此前月初的几次中断更短。一个长故障出现后，市场很自然地会问：它是偶然的长尾，还是下一次事故正在排队？预测市场把这个问题切成几个时间区间，看上去像在量一场暴雨会下多久。

规则里有几个容易忽略的地方。市场结算看GitHub Status页面记录的Critical Incident最长时长，普通服务降级不能自动算进去。用户觉得页面卡顿，和GitHub把事件标记成关键事故，是两套不同的语言。开发者可以在社交媒体上说“全站坏了”，结算还要等状态页给出事件起止时间。

这类故障的成本也很难只用分钟计算。一个团队可能正好在等CI跑完，另一个团队正在发布版本，第三个团队的客户只知道网页没有更新。服务恢复之后，工程师还要检查任务有没有重复执行，部署有没有半截成功，通知有没有漏发。对平台来说，事故结束的时间可能是状态页改成正常；对用户来说，事故结束还要再过一晚。

GitHub的基础设施越来越像一座城市。代码仓库是房屋，Actions像运输系统，Issues和Pull Requests像市政窗口。只要一个中心节点出问题，大家就会发现自己把很多工作都交给了同一张地图。云服务的方便也在这里留下了反面：当它停下来，团队突然不知道哪些环节原来依赖它。

市场押3至6小时，说明交易者更相信故障会被控制在中等区间。他们没有把12小时以上完全排除，因为大型平台总有遇到未知问题的可能。但除非出现新的容量事故、数据库压力或大规模网络问题，否则大多数中断最后会被拉回一个可以接受的时间段。

这并不意味着3至6小时很短。对一个正在赶发布的团队来说，三小时可能足够让一天的安排全部错位。互联网服务把停机时间写成一个数字，业务却会把它变成延迟、加班和一封解释邮件。市场希望预测故障会不会更长，工程师更想知道下次谁来值班。

月底前还可能出现新的事故，也可能什么都没有。无论答案落在哪个区间，GitHub的市场都提醒我们，今天的生产系统已经不只在办公室里运行。很多公司没有自己的机房，却有自己的停机表。状态页面上的一句“调查中”，对不同的人来说，可能是几分钟的烦躁，也可能是整晚的工作。

“最长关键事件”这个说法还会制造一种特别的紧张感。它并不是问整个月总共有多少次故障，也不是把所有小问题加起来，而是在找一场被官方标记为Critical Incident的最长中断。一次长达几小时的严重故障，可能比十次短暂的页面加载变慢更容易进入市场的记忆。标签本身也成了技术治理的一部分。

GitHub的用户分布很广，从个人开发者到跨国公司的工程团队都在同一张状态页面下等待。对个人来说，故障可能只是今天不能提交代码；对团队来说，它可能会打断发布流程、自动部署和安全检查。于是“停了多久”并不是单一体验。有人看着进度条，有人看着会议日历，还有人计算因为延迟而增加的云资源费用。

这类市场也提醒企业别把集中式服务当成没有成本的空气。使用GitHub很方便，团队不必维护服务器，也不必自己搭建协作工具。但便利意味着依赖，一旦服务中断，替代方案往往没有准备好。工程师平时最容易被忽略的工作，常常是在系统出问题时才突然变得重要。

月底的结算结果可能只是一个小时数，却会留下比小时数更长的余波。平台会发布复盘报告，客户会重新检查备份，开发者会在聊天群里开玩笑说“先别合并”。真正的可靠性，不是永远不出故障，而是出故障以后，所有人知道自己还有哪条路可以走。
